# セキュアコーディング

---

## 1. ルール（要約）

- 外部入力を信用してはいけない
- データは利用前に検証する
- 機密情報を適切に管理する
- 脆弱性を作り込まない
- セキュリティも品質の一部として考える
- 美しいコードとは安全で可読性の高いコードである

---

## 2. はじめに

可読性の高いコードは品質を向上させます。

しかし、可読性だけでは十分ではありません。

どれだけ美しく整理されたコードであっても、

- SQLインジェクション
- クロスサイトスクリプティング（XSS）
- 不適切な例外処理
- 機密情報の漏洩

などの脆弱性を含んでいては、
システムとしての品質は担保できません。

そのため、エルテクメソッドでは、

- 可読性
- 保守性
- セキュリティ

の3つを品質の柱として扱います。

本章では、日常的な業務開発において
最低限守るべきセキュアコーディングの原則を定義します。

---

## 基本思想

セキュリティとは特殊な技術ではありません。

特別な場面だけ意識するものではなく、
日々のコーディングの積み重ねによって実現されるものです。

例えば次のような考え方です。

- ユーザ入力を信用しない
- 想定外の値を受け入れない
- 例外を無視しない
- SQLを文字列連結しない
- 機密情報を露出しない

これらは高度なセキュリティ技術ではありません。

基本を徹底することが、
結果として大きな脆弱性を防ぐことにつながります。

セキュリティは開発の最後に考えるものではありません。

設計時から意識し、
コーディング時に実践し、
レビュー時に確認するものです。

---

## エルテクメソッドにおけるセキュアコーディング

本章は SEI CERT Java Coding Standard や
JPCERT/CC が公開するセキュアコーディングの考え方を参考に、
日常的な業務開発で特に重要と考えられるルールを
エルテクメソッド向けに再整理したものです。

エルテクメソッドは、
セキュリティ専門家向けの標準をそのまま採用するのではありません。

実務において、

- 実際に事故が発生しやすいこと
- コードレビューで発見できること
- 最低限守らなければならないこと

を中心にルール化します。

可読性の高いコードは品質を向上させます。

保守しやすいコードは運用コストを下げます。

そして、安全なコードはシステム品質を守ります。

エルテクメソッドでは、
セキュリティも品質の一部であると考えます。

## ルール選定方針

本章で扱うルールは、
JPCERT/CC セキュアコーディングおよび
Java コーディングスタンダード SEI CERT/Oracle版を
参考資料とする。

ルール作成にあたっては、

1. 元資料のルールを調査する
2. 採用／保留／非採用を判断する
3. エルテクメソッド向けに再構成する
4. 元ルールとの対応関係を記録する

という手順を取る。

Copilotを含む生成AIの推測のみを根拠として
ルールを新設してはならない。

また、
元資料との対応関係を説明できないルールは、
本章では採用しない。

---

## ルール識別子について

本章では、JPCERT/CC が公開する
「Java コーディングスタンダード SEI CERT/Oracle版」の
ルール識別子を記載しています。

例：

- IDS00-J
- ERR00-J
- MET00-J
- SEC02-J

識別子の意味は以下の通りです。

| 識別子 | 分類 |
|----------|----------|
| IDS | 入力値検査とデータの無害化 |
| DCL | 宣言と初期化 |
| EXP | 式 |
| NUM | 数値型とその操作 |
| STR | 文字列 |
| OBJ | オブジェクト指向 |
| MET | メソッド |
| ERR | 例外時の動作 |
| SEC | プラットフォームセキュリティ |

例えば、

- IDS00-J = SQLインジェクションを防ぐ
- ERR00-J = チェック例外を無視しない
- MET00-J = メソッド引数を検証する

を意味します。

本章では、元ルールとの対応関係を保持するため、
採用したルールの識別子を記載しています。

詳細は以下を参照してください。

https://www.jpcert.or.jp/java-rules/
