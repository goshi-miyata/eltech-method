# 構造化（分割）の原則

---

## 1. ルール（要約）
- 構造化はテスト単位で行う
- メソッドは単位機能で構成する
- 1つのメソッドに複数の機能を持たせない
- テスト項目が作成できる単位で分割する
- 美しいコードとは可読性の高いコードである

---

## 2. 解説（原文）

### コーディングのお作法（その２：構造化の勧め）

どんなオブジェクト指向言語でプログラミングを行っても、
最終的には構造化の考え方が必ず必要になります。
では、どの単位で構造化を行えばよいでしょう？
 なかなか、定義するのは難しい気もします。
ただし、答えは簡単。
テストの単位です。
基本的には、C2レベルのカバレッジを確保可能なコードとなります。
  
まず、誤ったコードを見てみましょう
  
```java
  private void func(bool A, int no)
  {
  
    if(A)
    {
      Switch(no)
        case 1: ・・・ break;
        case 2: ・・・ break;
          ・
          ・
          ・
        default: ・・・break;
    }
  }
```

このコードは何が問題でしょうか？
やはり、問題点が２点あります。
  
  
①ストーリが２つある
  基本的なメソッドの単位は、単位機能であるべきです。
  しかし、このメソッドの中には
    Aの判定
    noで分岐し対応する処理
  の二つの機能が存在します。
  つまり、開発者の中で機能が整理できていないという事になります。
  
②テスト項目が作成できない。
  上記は簡素化した例ですので項目の作成は可能ですが、
  このコードは、分岐の中に分岐を書いたコードとなります。
  例えば、Aの判定が複雑だったり、複数あったりした場合
  それにしたがって、全てのSwitch/Case文のマトリクステストが
  必要となります。
  
  では、正解コードはどうでしょう。
  
```java
  private void func(bool A, int no)
  {
  
    if(A) func2(no);
  }
  
  private void func2(no)
  {
      Switch(no)
        case 1: ・・・ break;
        case 2: ・・・ break;
          ・
          ・
          ・
        default: ・・・break;
    }
  }
```
  
この２つのメソッドのうち、
先のコードは、判定によりメソッドを呼ぶだけとなります。
func2が呼ばれる事だけ確認できれば問題ありません。
それに対し、後のfunc2()は、
引数でSwitchするテストだけを行うことになります。
  
メソッドが１行である事は全く問題はありません。
世の中のオープンソースのコードを実際に見てください。
メソッド１つだけを呼ぶメソッドが山ほどあります。

ところで、
こういったコーディングのお作法に関する意見があれば募集します。
先にも記載しましたが、絶対的に必要なのはコーディング規約で、
それさえあれば、それに従わざるを得ません。
まずはべき論でもよいですので、持論がある方はまずはメールください。
良ければ展開します。


美しいコードというのは、大前提として可読性の高いコードとなります。
